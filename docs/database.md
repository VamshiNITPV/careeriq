# CareerIQ — Database Design

**Document status:** Phase 1 · Living document
**Last updated:** 2026-09-01
**Engine:** PostgreSQL 16 with extensions `vector` (pgvector), `pg_trgm`, `pgcrypto`

Conventions used throughout — see [architecture.md](architecture.md) §4:
- Primary keys are `UUID` (UUIDv7, generated by the application).
- All timestamps are `TIMESTAMPTZ` in UTC.
- Every table has `created_at`; mutable tables also have `updated_at`.
- Soft deletes (`deleted_at`) only on `resumes` and `applications`.
- Foreign keys are `ON DELETE CASCADE` for owned children, `ON DELETE RESTRICT` where the reference
  is historical fact that must not silently vanish.

## 2. Enumerated types

Defined as native PostgreSQL `ENUM` types. Native enums give database-level validation; the cost is
that adding a value requires a migration, which is the correct amount of friction for these.

```sql
CREATE TYPE user_role          AS ENUM ('USER', 'ADMIN');
CREATE TYPE auth_provider      AS ENUM ('LOCAL', 'GOOGLE');
CREATE TYPE experience_level   AS ENUM ('INTERN','ENTRY','JUNIOR','MID','SENIOR','LEAD','PRINCIPAL');
CREATE TYPE education_level    AS ENUM ('NONE','HIGH_SCHOOL','DIPLOMA','BACHELORS','MASTERS','DOCTORATE');
CREATE TYPE employment_type    AS ENUM ('FULL_TIME','PART_TIME','CONTRACT','INTERNSHIP','TEMPORARY');
CREATE TYPE work_mode          AS ENUM ('ONSITE','HYBRID','REMOTE');
CREATE TYPE processing_status  AS ENUM ('PENDING','EXTRACTING','PARSING','EMBEDDING','COMPLETE','FAILED');
CREATE TYPE job_source         AS ENUM ('USER_SUBMITTED','DATASET_IMPORT','PARTNER_API','ADMIN_ENTRY');
CREATE TYPE job_status         AS ENUM ('ACTIVE','EXPIRED','DUPLICATE','ARCHIVED');
CREATE TYPE proficiency_level  AS ENUM ('BEGINNER','INTERMEDIATE','ADVANCED','EXPERT');
CREATE TYPE skill_requirement  AS ENUM ('REQUIRED','PREFERRED','NICE_TO_HAVE');
CREATE TYPE gap_severity       AS ENUM ('CRITICAL','HIGH','MEDIUM','LOW');
CREATE TYPE application_status AS ENUM ('SAVED','APPLIED','ASSESSMENT','INTERVIEW','OFFER','REJECTED','WITHDRAWN');
CREATE TYPE interview_status   AS ENUM ('CREATED','IN_PROGRESS','COMPLETED','ABANDONED');
CREATE TYPE question_difficulty AS ENUM ('EASY','MEDIUM','HARD','EXPERT');
CREATE TYPE notification_type  AS ENUM ('RESUME_PROCESSED','NEW_MATCHES','APPLICATION_REMINDER','INTERVIEW_READY','SYSTEM');
```

## 3. Table definitions

### 3.1 Identity & profile

#### `users`
The authentication record. Deliberately minimal — profile data lives in `profiles`.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | `UUID` | PK | UUIDv7 |
| `email` | `CITEXT` | NOT NULL, UNIQUE | Case-insensitive; `bob@x.com` = `Bob@x.com` |
| `password_hash` | `TEXT` | NULL | NULL for OAuth-only accounts |
| `auth_provider` | `auth_provider` | NOT NULL, DEFAULT `'LOCAL'` | |
| `oauth_subject` | `TEXT` | NULL, UNIQUE per provider | Google's stable `sub` claim |
| `role` | `user_role` | NOT NULL, DEFAULT `'USER'` | |
| `is_active` | `BOOLEAN` | NOT NULL, DEFAULT `TRUE` | Deactivation without deletion |
| `email_verified_at` | `TIMESTAMPTZ` | NULL | |
| `last_login_at` | `TIMESTAMPTZ` | NULL | |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | NOT NULL | |

```sql
CONSTRAINT ck_users_auth CHECK (
  (auth_provider = 'LOCAL'  AND password_hash IS NOT NULL) OR
  (auth_provider <> 'LOCAL' AND oauth_subject IS NOT NULL)
);
CREATE UNIQUE INDEX ux_users_oauth ON users (auth_provider, oauth_subject)
  WHERE oauth_subject IS NOT NULL;
```

> **Why `CITEXT` and not `LOWER(email)`:** a functional unique index works but every lookup must
> remember to lower-case. `CITEXT` makes correctness the default. The check constraint enforces
> ADR-014's rule that an account always has *some* usable credential.

#### `refresh_tokens`
Required by US-1.3 — refresh tokens must be revocable and support reuse detection.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | `UUID` | PK | |
| `user_id` | `UUID` | FK → `users.id` CASCADE, NOT NULL | |
| `token_hash` | `TEXT` | NOT NULL, UNIQUE | SHA-256 of the token. **Never store plaintext.** |
| `family_id` | `UUID` | NOT NULL | Rotation chain identifier |
| `expires_at` | `TIMESTAMPTZ` | NOT NULL | |
| `revoked_at` | `TIMESTAMPTZ` | NULL | |
| `replaced_by_id` | `UUID` | FK → self, NULL | Rotation link |
| `user_agent`, `ip_address` | `TEXT`, `INET` | NULL | Audit |
| `created_at` | `TIMESTAMPTZ` | NOT NULL | |

> **Reuse detection:** presenting a token whose `revoked_at` is set means it was already rotated —
> either theft or a race. The response is to revoke the entire `family_id`, forcing re-login.

#### `profiles`
One-to-one with `users`. Holds career preferences that feed ranking (ADR-005).

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID` | PK |
| `user_id` | `UUID` | FK → `users.id` CASCADE, **UNIQUE** (enforces 1:1) |
| `full_name`, `headline` | `TEXT` | |
| `phone`, `location`, `country_code` | `TEXT` | |
| `linkedin_url`, `github_url`, `portfolio_url` | `TEXT` | |
| `summary` | `TEXT` | |
| `years_of_experience` | `NUMERIC(4,1)` | Derived from resume, user-overridable |
| `current_experience_level` | `experience_level` | |
| `highest_education` | `education_level` | |
| `target_roles` | `TEXT[]` | e.g. `{Backend Engineer, ML Engineer}` |
| `preferred_locations` | `TEXT[]` | |
| `preferred_work_modes` | `work_mode[]` | |
| `preferred_employment_types` | `employment_type[]` | |
| `min_salary_expectation` | `NUMERIC(12,2)` | |
| `salary_currency` | `CHAR(3)` | ISO 4217 |
| `open_to_relocation` | `BOOLEAN` | |
| `preferences_updated_at` | `TIMESTAMPTZ` | Drives recommendation cache invalidation (ADR-008) |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | |

> **Why arrays instead of join tables** for `target_roles` and `preferred_locations`: these are
> user free-text preferences with no shared identity or attributes. A join table would add two
> tables and buy nothing. Skills are the opposite case — they *are* shared entities — which is why
> they get `skills` + `candidate_skills`.

### 3.2 Resume & career profile

#### `resumes`
The logical resume. The file itself belongs to a version.

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID` | PK |
| `user_id` | `UUID` | FK → `users.id` CASCADE, NOT NULL |
| `title` | `TEXT` | e.g. "Backend-focused resume" |
| `is_primary` | `BOOLEAN` | Exactly one primary per user |
| `current_version_id` | `UUID` | FK → `resume_versions.id`, NULL until first parse |
| `deleted_at` | `TIMESTAMPTZ` | Soft delete |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | |

```sql
CREATE UNIQUE INDEX ux_resumes_one_primary ON resumes (user_id)
  WHERE is_primary AND deleted_at IS NULL;
```

#### `resume_versions`
Immutable snapshots. Required by US-2.5 and US-7.2 AC2 (analytics by resume version).

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID` | PK |
| `resume_id` | `UUID` | FK → `resumes.id` CASCADE, NOT NULL |
| `version_number` | `INTEGER` | NOT NULL, unique per resume |
| `storage_key` | `TEXT` | NOT NULL — UUID object key, **never the client filename** (ADR-014) |
| `original_filename` | `TEXT` | Display metadata only |
| `mime_type` | `TEXT` | Determined by magic bytes |
| `file_size_bytes` | `INTEGER` | CHECK ≤ 5242880 |
| `content_hash` | `TEXT` | SHA-256 — skips reprocessing identical re-uploads |
| `raw_text` | `TEXT` | Full extracted text |
| `parsed_sections` | `JSONB` | Detected sections with text spans |
| `parsed_entities` | `JSONB` | Raw NLP output with confidences and source spans (US-2.3 AC2) |
| `processing_status` | `processing_status` | NOT NULL, DEFAULT `'PENDING'` |
| `processing_error` | `TEXT` | Populated on `FAILED` |
| `processed_at` | `TIMESTAMPTZ` | |
| `created_at` | `TIMESTAMPTZ` | No `updated_at` — versions are immutable |

```sql
CREATE UNIQUE INDEX ux_resume_versions_number ON resume_versions (resume_id, version_number);
CREATE INDEX ix_resume_versions_hash ON resume_versions (content_hash);
```

> **Why JSONB for `parsed_entities`:** extractor output is heterogeneous and its shape will change
> as the NLP pipeline improves. Normalizing it into rigid columns would force a migration on every
> parser change. Structured data that the *application* depends on — skills, education, experience —
> is promoted out of JSONB into real tables below. JSONB holds the provenance; relational tables
> hold the truth.

#### `skills`
The shared, canonical skill taxonomy.

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID` | PK |
| `name` | `TEXT` | NOT NULL, UNIQUE — canonical form, e.g. `PostgreSQL` |
| `normalized_name` | `TEXT` | NOT NULL, UNIQUE — lookup key, e.g. `postgresql` |
| `category` | `TEXT` | `language`, `framework`, `database`, `cloud`, `tool`, `soft_skill` |
| `aliases` | `TEXT[]` | `{postgres, psql, pg}` — resolves extraction variants |
| `parent_skill_id` | `UUID` | FK → self, NULL — hierarchy (React → JavaScript) |
| `demand_score` | `NUMERIC(5,4)` | Fraction of active jobs requiring it; drives gap severity |
| `is_verified` | `BOOLEAN` | Admin-reviewed vs auto-created from extraction |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | |

```sql
CREATE INDEX ix_skills_trgm ON skills USING GIN (normalized_name gin_trgm_ops);
CREATE INDEX ix_skills_aliases ON skills USING GIN (aliases);
```

> **Why a shared taxonomy rather than free-text skills on each side:** matching a candidate's
> "Postgres" to a job's "PostgreSQL" is the entire point. Aliases plus trigram search resolve
> variants to one canonical id, so the skill-match dimension (ADR-005) compares ids, not strings.
> `parent_skill_id` lets us later credit partial matches — React implies JavaScript.

#### `candidate_skills`

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID` | PK |
| `user_id` | `UUID` | FK → `users.id` CASCADE, NOT NULL |
| `skill_id` | `UUID` | FK → `skills.id` RESTRICT, NOT NULL |
| `proficiency` | `proficiency_level` | |
| `years_of_experience` | `NUMERIC(4,1)` | |
| `source_version_id` | `UUID` | FK → `resume_versions.id` SET NULL — provenance |
| `extraction_confidence` | `NUMERIC(4,3)` | 0.000–1.000 |
| `is_user_verified` | `BOOLEAN` | NOT NULL, DEFAULT `FALSE` |
| `last_used_year` | `SMALLINT` | Recency signal |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | |

```sql
CREATE UNIQUE INDEX ux_candidate_skills ON candidate_skills (user_id, skill_id);
```

> **`is_user_verified` implements US-2.4 AC2:** a re-parse may update rows where it is `FALSE`, and
> must never overwrite rows where it is `TRUE`. This is the idempotency rule that makes background
> re-processing (ADR-009) safe.

#### `education_records`, `work_experiences`, `projects`, `certifications`
Promoted out of JSONB because ranking and gap analysis query them directly. All share the same
shape: `user_id` FK, `source_version_id` provenance, `extraction_confidence`,
`is_user_verified`, plus their own fields.

- **`education_records`** — `institution`, `degree`, `field_of_study`, `education_level`,
  `start_date`, `end_date`, `grade`, `is_current`
- **`work_experiences`** — `company_name`, `title`, `employment_type`, `location`, `work_mode`,
  `start_date`, `end_date`, `is_current`, `description`, `highlights TEXT[]`
- **`projects`** — `name`, `description`, `url`, `repository_url`, `highlights TEXT[]`,
  `start_date`, `end_date`
- **`certifications`** — `name`, `issuer`, `credential_id`, `credential_url`, `issued_date`,
  `expires_date`

Each also carries a `_skills` join to `skills` where relevant (e.g. `project_skills`), so
"which projects demonstrate Kubernetes" is answerable.

| `source_url`, `external_id` | `TEXT` | |
| `title` | `TEXT` | NOT NULL |
| `normalized_title` | `TEXT` | Grouping for analytics |
| `description_raw` | `TEXT` | NOT NULL — original text, never mutated |
| `description_clean` | `TEXT` | Normalized text used for embedding |

| `content_hash` | `TEXT` | NOT NULL — first-pass dedup (US-3.2) |
| `canonical_job_id` | `UUID` | FK → self, NULL — set when `status = 'DUPLICATE'` |
| `status` | `job_status` | NOT NULL, DEFAULT `'ACTIVE'` |
| `posted_at`, `expires_at` | `TIMESTAMPTZ` | |
| `parsing_status` | `processing_status` | |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | |

```sql
CREATE INDEX ix_jobs_active         ON jobs (status, posted_at DESC) WHERE status = 'ACTIVE';
CREATE INDEX ix_jobs_content_hash   ON jobs (content_hash);
CREATE INDEX ix_jobs_title_trgm     ON jobs USING GIN (normalized_title gin_trgm_ops);
CREATE INDEX ix_jobs_location       ON jobs (country_code, location);
CREATE UNIQUE INDEX ux_jobs_external ON jobs (source, external_id)
  WHERE external_id IS NOT NULL;   -- makes dataset import idempotent (US-3.3 AC1)
```

> **Two-stage deduplication (US-3.2):** `content_hash` catches exact re-posts cheaply in an index
> lookup. Near-duplicates — same role reworded, or posted by an agency and the employer — are
> caught by embedding cosine similarity above threshold, checked only against jobs from the same
> company or with a similar title. The loser gets `status = 'DUPLICATE'` and
> `canonical_job_id` pointing at the survivor; it is retained rather than deleted so that
> applications referencing it stay valid.

| Column | Type | Notes |
|---|---|---|

| `job_id` | `UUID` | FK → `jobs.id` CASCADE, NOT NULL |
| `skill_id` | `UUID` | FK → `skills.id` RESTRICT, NOT NULL |

| `min_years` | `NUMERIC(4,1)` | |
| `extraction_confidence` | `NUMERIC(4,3)` | |
| `created_at` | `TIMESTAMPTZ` | |

> active jobs is this skill `REQUIRED`?"

### 3.4 Embeddings

Both embedding tables share the same design. Dimension `768` matches the planned
`sentence-transformers` model; it is fixed at migration time because `pgvector` requires a declared
dimension.

#### `job_embeddings` / `candidate_embeddings`

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID` | PK |
| `job_id` / `resume_version_id` | `UUID` | FK CASCADE, NOT NULL |
| `embedding` | `VECTOR(768)` | NOT NULL |
| `model_name` | `TEXT` | NOT NULL — e.g. `all-mpnet-base-v2` |
| `model_version` | `TEXT` | NOT NULL |
| `dimensions` | `SMALLINT` | NOT NULL |
| `source_text_hash` | `TEXT` | NOT NULL — skip re-embedding unchanged text |
| `created_at` | `TIMESTAMPTZ` | NOT NULL |

```sql
CREATE UNIQUE INDEX ux_job_embeddings ON job_embeddings (job_id, model_name, model_version);

CREATE INDEX ix_job_embeddings_hnsw ON job_embeddings
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
```

> **Why HNSW and not IVFFlat:** IVFFlat needs to be built *after* data exists and re-built as the
> corpus grows, and its recall degrades if `lists` is set for the wrong table size. HNSW builds
> incrementally, handles inserts gracefully, and gives better recall at the same latency. It costs
> more memory and build time — acceptable at our scale.
>
> **Why `model_name` + `model_version` are part of the unique key** (ADR-007): changing embedding
> models makes existing vectors meaningless. Keying on the model lets old and new vectors coexist
> during a re-embedding migration, so search keeps working while backfill runs.

### 3.5 Matching

#### `job_matches`
A materialized score, cached so a dashboard load does not recompute everything.

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID` | PK |
| `user_id` | `UUID` | FK → `users.id` CASCADE, NOT NULL |
| `job_id` | `UUID` | FK → `jobs.id` CASCADE, NOT NULL |
| `resume_version_id` | `UUID` | FK → `resume_versions.id` CASCADE — which resume produced it |
| `overall_score` | `NUMERIC(5,2)` | 0.00–100.00 |
| `semantic_score`, `skill_score`, `experience_score`, `education_score`, `location_score`, `salary_score` | `NUMERIC(5,4)` | Each 0.0–1.0 (US-4.1 AC2) |
| `matched_skill_ids`, `missing_skill_ids`, `partial_skill_ids` | `UUID[]` | Drives the explanation (US-4.2) |
| `explanation` | `JSONB` | Per-dimension human-readable reasons |
| `ranking_version` | `TEXT` | NOT NULL — weight-set identifier, e.g. `v1-hand-tuned` |
| `computed_at` | `TIMESTAMPTZ` | NOT NULL |
| `is_stale` | `BOOLEAN` | Set when preferences or resume change |

```sql
CREATE UNIQUE INDEX ux_job_matches ON job_matches (user_id, job_id, resume_version_id, ranking_version);
CREATE INDEX ix_job_matches_rank ON job_matches (user_id, overall_score DESC)
  WHERE NOT is_stale;
```

> **`ranking_version` is what makes ADR-005's migration path testable.** When a learned ranker
> arrives, its scores are written under a new `ranking_version` alongside the hand-tuned ones. Both
> can be evaluated against the same labelled set, and A/B comparison is a `WHERE` clause rather
> than a data migration.

### 3.6 Skill gaps & learning

| `frequency_in_target_jobs` | `NUMERIC(5,4)` | Fraction of target jobs requiring it |
| `computed_at` | `TIMESTAMPTZ` | |

```sql
CREATE INDEX ix_applications_status ON applications (user_id, status, last_status_change_at DESC);
```

> **Why `RESTRICT` on `job_id` and `resume_version_id`:** an application is historical fact. If
> deleting a job silently cascaded away applications, analytics (US-7.2) would quietly lose data
> and the funnel would be wrong with no error. `RESTRICT` forces the deletion path to deal with it.
>
> **Why `match_score_at_apply` is denormalized:** ranking weights and the corpus change over time.
> Answering "do high-match applications convert better?" requires the score *as it was at the time
> of applying*, not as recomputed today.

## 4. Index summary

| Purpose | Index |
|---|---|
| Vector recall (ADR-006 stage 1) | `hnsw (embedding vector_cosine_ops)` on both embedding tables |
| Active job filtering | Partial `(status, posted_at DESC) WHERE status='ACTIVE'` |
| Skill name resolution | GIN trigram on `skills.normalized_name`; GIN on `skills.aliases` |
| Ranked recommendations | Partial `(user_id, overall_score DESC) WHERE NOT is_stale` |
| Application funnel | `(user_id, status, last_status_change_at DESC)` |
| Idempotent import | Partial unique `(source, external_id) WHERE external_id IS NOT NULL` |
| Unread notifications | Partial `(user_id, created_at DESC) WHERE NOT is_read` |

Partial indexes are used heavily. They are smaller, faster, and encode a business rule — "there is
at most one primary resume per user" is enforced by a unique partial index rather than application
code that can be bypassed.

## 5. Migration strategy

- Every change is an Alembic revision, reviewed in the diff. No manual DDL, including locally (ADR-004).
- Extensions (`vector`, `pg_trgm`, `citext`, `pgcrypto`) are enabled in the first migration.
- Enum values are added via migration; `ALTER TYPE ... ADD VALUE` cannot run inside a transaction
  block in older Postgres, so those revisions are marked accordingly.
- Adding a non-nullable column to a populated table is always three steps: add nullable → backfill →
  set `NOT NULL`. Never one step.
- HNSW index creation on a large table is slow and locking; it uses `CONCURRENTLY` once the corpus
  is non-trivial.
